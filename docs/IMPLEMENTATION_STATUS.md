# 구현 현황과 작업 예정 순서



기준일: **2026-09-15** · 대상: 현재 저장소의 코드

이번 점검에서 앱·테스트 공통 빌드, 저장소 변경 알림 통합, 작업 중 새로고침 예약,
아이콘 교체, Git 매뉴얼의 별도 라이선스 데이터 분리, 무설치 전용 패키징과 소스·해시
생성을 반영했습니다. Windows 외부 라이브러리 대응 소스는 자동 수집·서명 검증합니다.
Mac/Linux 실환경 검증과 해당 플랫폼의 외부 라이브러리 대응 소스 확보는 남아
있습니다. 세부 내용은 [무설치 배포](PORTABLE_DISTRIBUTION.md)를 참고하세요.

이 문서는 실제 구현 현황과 앞으로의 작업 순서를 기록합니다. 제품의 전체 목표는 [필수 기능 명세](필수%20기능%20명세.md), 실행 방법은 [Windows 프로토타입 안내](WINDOWS_PROTOTYPE.md), 내부 구조는 [아키텍처](ARCHITECTURE.md)를 참고합니다. 과거 문서에 기록된 초기 구현 상태와 차이가 있으면 현재 코드를 기준으로 이 문서를 갱신합니다.

## 상태를 구분하는 기준

- **구현**: 아래에 적힌 범위가 UI 또는 실행 코드에 연결되어 있습니다. 해당 기능군의 모든 고급 옵션까지 완성했다는 뜻은 아닙니다.
- **부분 구현**: 기본 동작은 있지만 전체 명세를 충족하려면 추가 작업이 필요합니다.
- **미구현**: 현재 사용자용 화면이나 실행 흐름이 없습니다. 시스템 Git에 기능이 있거나 기존 설정을 이용할 수 있다는 것만으로 구현 완료로 보지 않습니다.
- **범위 결정 필요**: 명세에서도 최초 정식 버전 포함 여부나 구현 방식이 확정되지 않은 항목입니다.

코드에 기능이 존재하는 것과 모든 환경에서 검증이 끝난 것은 구분합니다. 아래의 검증 범위는 별도 절에 기록합니다.

### 변경 파일과 커밋

| 기능 | 현재 동작 |
|---|---|
| 상태 조회 | 작업 디렉터리와 커밋할 파일을 나누어 표시합니다. 외부 파일 변경은 로컬파일 새로고침으로 반영합니다. |
| 파일 선택과 체크 분리 | 파일명 클릭은 diff 조회, 체크박스는 Stage/Unstage 대상 선택입니다. |
| 전체 체크 | 각 목록에서 전체 체크 및 부분 체크 상태를 표시합니다. |
| 체크한 파일 Stage/Unstage | 체크한 파일의 변경을 staging 영역에 넣거나 뺍니다. |
| 전체파일 Stage/Unstage | 체크 여부와 관계없이 해당 목록의 모든 파일에 적용합니다. |
| 첫 커밋 이전 Unstage | HEAD가 없는 저장소에서도 파일을 보존하며 staging에서 제외합니다. |

| 커밋 실행 | staging 영역 전체를 커밋합니다. 목록의 체크 여부로 커밋 대상을 다시 제한하지 않습니다. |
| 성공 후 갱신 | 커밋 성공 시 입력을 비우고 파일 상태·브랜치·이력을 갱신합니다. |

### 브랜치

| 기능 | 현재 동작 |
|---|---|
| 로컬 브랜치 목록 | 드롭다운에서 로컬 브랜치를 조회합니다. |
| 즉시 전환 | 사용자가 항목을 선택하면 바로 전환합니다. 프로그램이 목록을 갱신하는 동작은 전환을 실행하지 않습니다. |
| 새 브랜치 | 현재 HEAD에서 분리해 생성하고 새 브랜치로 이동합니다. |
| 이름 변경 | 현재 로컬 브랜치의 이름을 변경합니다. 원격 이름 변경은 별도입니다. |
| 현재 브랜치 삭제 | 삭제 대상 자신을 제외하고 main → master → 나머지 첫 로컬 브랜치 순으로 자동 이동한 뒤 삭제합니다. |
| 브랜치 재선택·삭제 보호 | 현재 브랜치를 다시 선택하면 전환 명령을 실행하지 않습니다. 로컬 브랜치가 하나만 남으면 삭제 버튼을 비활성화합니다. |
| 일반·강제 삭제 | 기본은 `branch -d`, 체크 시 `-D`입니다. 강제 삭제 체크를 켤 때마다 경고하고 거부하면 해제합니다. |
| 연결된 원격 삭제 | 체크한 경우 현재 브랜치의 upstream에 해당하는 원격 브랜치도 삭제합니다. upstream 설정이 없으면 체크를 비활성화합니다. |
| 삭제 오류 처리 | 전환 실패 시 삭제를 중단합니다. 로컬 삭제 실패 시 원격 삭제를 하지 않으며, 로컬 성공·원격 실패는 부분 성공으로 안내합니다. |

원격 삭제 체크 활성화는 **연결 설정이 있다는 뜻**이며 실제 서버 접속이나 삭제 권한을 미리 검증했다는 뜻은 아닙니다.

### 동기화

| 기능 | 현재 동작 |
|---|---|
| 단일 동기화 버튼 | Fetch/Pull/Push를 한 버튼에서 현재 상태에 따라 표시합니다. |
| Fetch 선행 | 앱 시작·저장소 열기·브랜치 변경 등 새 작업 문맥에서는 Fetch부터 진행합니다. 성공 전에는 Pull/Push를 허용하지 않습니다. |
| 원격 비교 | 현재 upstream과의 ahead/behind를 비교하고 받을/올릴 커밋 수를 표시합니다. |
| Pull | 원격만 앞서면 fast-forward 방식으로 받습니다. 작업 중인 변경이 있으면 차단합니다. |
| Push | 로컬만 앞서면 비교한 upstream 브랜치에 일반 Push를 합니다. 강제 Push는 제공하지 않습니다. |
| 양쪽 이력 분기 | Pull 해결을 우선하도록 표시하고 Push를 차단합니다. 자동으로 이력을 통합하지는 않습니다. |
| 실행 전 재검사 | 확인 이후 상태가 바뀌면 Fetch부터 다시 시작하도록 합니다. 실패 시에도 Fetch 상태로 돌아갑니다. |
| 연결 설정 검사 | detached HEAD, 첫 커밋 이전, 주소 불일치, 여러 Push 주소, 비표준 추적 매핑 등의 상황을 제한합니다. upstream은 GUI에서 설정합니다. |

|---|---|

| 원격 브랜치 탐색 | 설정 화면에서 목록 Fetch 후 대상 선택 또는 직접 입력 |
| 최초 Push | 상단 Fetch로 대상 부재 확인 후 게시, upstream 연결, 게시 직전 동명 브랜치 생성 시 덮어쓰기 차단 |

| 생성 보호 | 비어 있지 않은 대상 거부, 실패 시 기존 활성 저장소 유지, 폴더 자동 삭제 없음 |

### 고급 커밋·병합·충돌 해결 (작업 순서 6·7 완료)

| 기능 | 현재 동작 |
|---|---|

| 줄 선택 Diff | 추가/삭제 줄 체크로 Stage/Unstage, 신규·삭제 파일 포함, 역방향 패치·상태 재검사·apply --check |

### 이력 수정·복구 확장 (작업 순서 8 완료)

선형 1~200개 커밋의 순서 변경·Pick/Reword/Edit/Squash/Fixup/Drop, Edit의 Amend·Continue/Abort·3-way 연결을 제공합니다. HEAD reflog와 앱 복구 참조를 조회하고 새 브랜치 보존·깨끗한 브랜치 되돌리기·삭제 Stash 복원·복구 참조 삭제를 실행합니다. 실행 전 HEAD·계획 보관, 상태 재검사, 무시 파일 충돌 보호를 적용합니다.

[사용법과 제한](HISTORY_REWRITE_AND_RECOVERY.md): 병합 구조 유지·exec·자동 Undo는 제외하며, 파일 백업은 폴더를 열어 수동 복사합니다.

## 4. 우선순위와 작업 예정 순서

아래는 현재 구현과 의존관계를 고려한 **제안 작업 순서**입니다. 개발 착수나 완료 날짜를 확정한 일정은 아닙니다. 새로운 요청이 들어오면 순서를 조정하고 이 문서를 갱신합니다.

- **P1**: 일상적인 Git 작업을 앱 안에서 완료하는 기능
- **P2**: 협업·완성도·원격 작업공간 확장
- **P3**: 고급 기능과 추가 플랫폼

P0는 높은 중요도를 뜻하며 반드시 표의 모든 P1보다 먼저 착수한다는 뜻은 아닙니다. 위 표는 의존관계와 작은 기능 단위를 고려한 기본 순서입니다. 이번에는 요청에 따라 Diff·History와 이력 메뉴의 보호 검사를 먼저 구현했습니다. 4번의 공통 보호 정책은 나머지 위험 작업을 확장할 때 함께 적용합니다.

공통 구조도 기능 작업에 맞춰 확장합니다. 2~4번에서 구조화된 Git 요청·명령 미리보기·검증을 도입하고, 7~8번에서 복구 정책을 강화하며, 12번에서 로컬/SSH executor를 분리합니다. 기본 민감정보 보호와 오류 처리는 각 기능에 함께 적용하고 11번까지 미루지 않습니다.

## 6. 문서 갱신 규칙

1. 기능 구현 시 해당 항목의 상태와 제한을 함께 갱신합니다.
2. 완료 판단은 UI 연결·실제 Git 결과·필요한 테스트·사용 안내를 확인한 뒤 기록합니다.
3. 부분 구현은 남은 작업을 지우지 말고 다음 순서와 연결합니다.
4. 우선순위가 바뀌면 선행 조건과 변경 이유를 함께 기록합니다.
5. 테스트하지 않은 운영체제·서비스·규모는 검증 완료로 표시하지 않습니다.
