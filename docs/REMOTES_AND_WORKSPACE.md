# 원격 연결·최초 Push와 저장소 생성

작업 순서 2번과 3번의 사용 안내입니다.

## remote와 upstream 설정

Workspace의 **원격 · 브랜치 연결**을 엽니다. 저장소가 열려 있을 때 사용할 수 있습니다.

1. **＋ 새 원격 추가**에서 이름(보통 `origin`)과 서버 URL 또는 로컬 저장소 경로를 입력하고 **원격 저장**을 누릅니다. HTTPS·SSH 주소의 인증은 기존 Git credential helper/SSH 설정을 사용합니다. 주소에 토큰이나 비밀번호를 넣는 대신 인증 도구를 사용하세요.
2. 등록된 원격을 선택하면 가져오기 주소를 바꿀 수 있습니다. 현재 Push 주소도 표시합니다. 별도 Push 주소가 있다면 **Push 주소 통일**로 저장된 가져오기 주소를 해당 저장소의 Push 주소로 설정할 수 있습니다. 입력 중인 주소는 먼저 **원격 저장**으로 저장해야 합니다.
3. **원격 브랜치 목록 가져오기**로 브랜치를 조회합니다. 이 버튼은 파일을 바꾸거나 Push하지 않습니다.
4. **대상 원격 브랜치**에서 기존 브랜치를 선택하거나 새 이름을 입력하고 **현재 브랜치 연결 저장**을 누릅니다. 현재 로컬 브랜치에 연결할 remote와 `refs/heads/<대상>`을 저장합니다. 아직 서버에 없는 이름도 지정할 수 있습니다.

remote는 서버 주소의 별명이고, upstream은 현재 브랜치가 기본으로 비교하고 주고받을 원격 브랜치입니다. 로컬 이름과 원격 이름이 달라도 연결할 수 있습니다. 원격 이름은 영문·숫자·밑줄·점·하이픈을 사용하며, 브랜치 이름은 Git으로 검증합니다.

**원격 연결 제거**는 확인 후 이 저장소의 remote와 로컬 추적 정보·연결 설정을 제거합니다. 서버 저장소나 서버 브랜치를 삭제하지 않습니다. 기존 원격 이름 자체의 변경, 임의 fetch refspec 편집, 여러 Push 목적지 관리는 제공하지 않습니다.

설정 변경과 이 화면의 Fetch 후에는 상단 동기화 버튼의 Fetch 권한을 초기화합니다. 원격 설정을 다시 읽는 과정에서 오류가 발생하면 Git 오류를 보여줍니다. upstream의 remote와 대상 브랜치는 순서대로 저장되므로 둘 중 일부만 저장된 경우 연결을 다시 설정해야 합니다.

## 최초 Push

1. 로컬에 첫 커밋을 만듭니다. 새 브랜치라면 올릴 커밋을 준비합니다.
2. 위 화면에서 원격과 대상 브랜치를 저장합니다.
3. 상단 **Fetch · 원격 확인**을 누릅니다. 대상 원격의 브랜치들을 가져오고 없어진 추적 브랜치를 정리한 뒤 비교합니다.
4. 대상이 없으면 버튼이 **최초 Push · 브랜치 게시**로 바뀝니다. 클릭하면 현재 HEAD를 지정한 서버 브랜치에 올리고 upstream을 연결합니다.

대상이 이미 있으면 기존 비교 규칙을 사용합니다. 원격이 앞서면 Pull, 로컬이 앞서면 Push이며 양쪽 이력이 갈라지면 Pull 해결을 우선하고 자동 게시를 막습니다. 최초 Push 이후에도 각 클릭은 표시된 작업 하나만 실행합니다.

Fetch 이후 다른 사람이 같은 원격 브랜치를 만들면 최초 Push를 거절합니다. 새 브랜치 생성 시에만 대상이 여전히 없다는 조건(`--force-with-lease=<ref>:`)을 사용하며, 기존 브랜치를 강제로 덮어쓰는 기능이 아닙니다. 실패하면 다시 Fetch하여 비교해야 합니다. 서버의 보호 규칙이나 권한도 그대로 적용됩니다.

가져오기/Push 주소가 다르거나 Push 주소가 여러 개인 설정, 로컬 브랜치를 upstream으로 쓰는 설정, 기본 `refs/remotes/<remote>/<branch>`와 다른 추적 매핑은 동기화를 제한합니다. 환경의 Global 설정 때문에 여러 Push 주소가 남는 경우에는 해당 설정 출처를 별도로 정리해야 합니다.

## 새 저장소 만들기

Workspace의 **새 저장소**에서 대상 폴더의 전체 경로와 첫 브랜치 이름(기본 `main`)을 입력합니다. 새 경로, 빈 폴더, 파일이 있는 기존 프로젝트 폴더를 사용할 수 있습니다. 기존 파일은 그대로 유지되며 자동으로 Stage하거나 커밋하지 않습니다. 성공하면 Workspace에 등록하고 바로 엽니다. 원하는 파일을 선택해 Stage·커밋하면 됩니다. 이미 Git 저장소인 폴더는 **저장소 추가**로 여세요.

생성이 완료되면 메인 화면에 대상 경로와 완료 안내가 표시됩니다. Workspace 등록은 즉시 저장되므로 다른 Git 작업 때문에 열기를 기다리거나 화면 전환을 취소해도 목록에 남습니다. 열기에 실패한 경우에는 생성 완료와 열기 실패를 구분해 안내합니다. 완료 안내는 **닫기**로 닫을 수 있으며 작업 로그에도 남습니다.

bare 저장소 생성과 기존 저장소 재초기화는 이 화면에서 제공하지 않습니다.

## Clone

Workspace의 **Clone**에서 URL 또는 로컬 저장소 경로, 비어 있는 대상 폴더의 전체 경로를 입력합니다. 브랜치/태그 입력은 선택 사항이며 비우면 서버의 기본 브랜치를 사용합니다.

| 방식 | 동작 |
|---|---|
| 전체 | 기본 Git clone으로 이력과 파일을 가져옵니다. |
| Shallow | 지정한 깊이(기본 100)의 최근 이력을 가져옵니다. 기본적으로 선택 브랜치만 가져오며, 오래된 이력을 활용하는 작업은 제한될 수 있습니다. |
| Partial | `--filter=blob:none`으로 파일 내용의 전송을 늦춥니다. 서버 지원이 필요하며 현재 파일 checkout과 이후 조회에서 내용을 추가로 내려받을 수 있습니다. 서버가 지원하지 않으면 Git이 경고하고 필터 없이 진행할 수 있습니다. |

로컬 경로에서도 Shallow/Partial 옵션을 적용하도록 두 방식에는 `--no-local`을 사용합니다. 진행 화면에 Git 전송 메시지를 표시하고 성공하면 저장소를 등록합니다. 성공한 Clone의 origin과 기본 upstream은 Git clone이 만든 설정을 사용하되, 앱의 동기화는 다시 Fetch부터 시작합니다.

Git 실행 중 창을 닫거나 중복 생성하지 못하도록 합니다. Clone·Fetch는 화면의 **현재 작업 중단**으로 중단할 수 있고 명령별 시간 제한도 적용합니다. 실패 시 원래 활성 저장소를 유지하고 대상 폴더를 자동 삭제하지 않습니다. 다시 시도할 때 대상 폴더 상태를 확인하세요. [작업 중단 정책](OPERATIONS_AND_RECOVERY.md)을 참고하세요. 앱 자체 로그인, shallow 이력 확장과 partial 필터 변경 화면은 후속 기능입니다.

## Workspace 보완

- 저장소를 우클릭하면 **표시 이름 변경**, **저장소 경로 다시 지정**, **목록에서 제거**를 사용할 수 있습니다.
- 표시 이름은 Workspace에서만 사용합니다. 실제 디렉터리 이름과 상단 폴더명은 바꾸지 않습니다. 빈 이름은 원래 폴더명으로 돌아갑니다.
- 경로 재지정은 새 경로가 Git 저장소인지 검증하고 중복 등록을 막습니다. 즐겨찾기·표시 이름·초안을 새 등록 경로로 옮깁니다. 실제 폴더를 이동하는 기능은 아닙니다.
- 목록 제거는 등록 정보와 해당 초안만 지웁니다. 파일·Git 기록은 유지합니다. 현재 저장소를 제거하면 다음 저장소를 열고, 남은 저장소가 없으면 선택을 해제합니다.
- 드래그 또는 기존 ↑/↓로 정렬합니다. 즐겨찾기 그룹이 항상 위에 오며 다른 그룹으로 드래그해도 즐겨찾기 여부는 바뀌지 않습니다.
- 저장소별 제목·상세 설명 초안을 QSettings에 저장하고 앱 재실행 후 복원합니다. 파일 체크와 Stage 상태를 별도로 저장하는 기능은 아닙니다. Stage는 Git Index에 있는 실제 상태를 다시 조회합니다.

## 검증 범위

임시 로컬·bare 원격 저장소로 remote 등록·수정·제거, upstream 설정, 빈 원격 최초 Push, 게시 직전 동명 브랜치 생성 차단과 재Fetch, 실패 후 Fetch 잠금을 확인합니다. 전체/Shallow/필터 지원 서버 Partial Clone, 기존 파일이 있는 대상 거부, GUI 생성·Clone 후 Workspace 등록도 검사합니다. Workspace 표시명·경로·순서·목록 제거·초안 복원을 확인합니다.

실제 GitHub/GitLab 조직 인증, 서버 보호 정책 조합, 대규모 저장소 전송과 네트워크 중단 시나리오를 모두 검증한 것은 아닙니다.
